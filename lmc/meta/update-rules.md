# 更新规则

本文件是 `lmc/` 知识库的强制规范，约束所有文档的新增、修改与删除。规则本身如需调整，
直接改写本文件，改写后同样只呈现终态。

## 1. 核心原则

### 1.1 只呈现终态，不保留迭代痕迹

文档描述的是「代码当前就是这样」，而不是「文档是怎样写出来的」。任何一次更新完成后，
读者拿到的必须是一份自洽的终态文档，看不到更新过程。

禁止出现：

- 修订记录、变更日志、「本次更新」「上一版」「原先认为」等过程性叙述；
- 被推翻的旧结论，包括用删除线、括号补充、「注：原方案已废弃」等形式保留的旧说法；
- 版本演进式对比，例如「早期版本在客户端做，现在改到服务端」；
- 草稿段落、`TODO`、「待补充」「后续再写」这类占位内容。

正确的做法是直接删除旧结论、写入新结论，并让上下文重新自洽。

唯一的例外是索引用途的文档：`lmc/modules/README.md`、`lmc/features/README.md` 与知识库
[README](../README.md) 的「覆盖范围」小节允许列出尚未撰写、计划撰写的主题，因为登记
计划正是索引的职责。除此以外，任何文档都不得包含未完成内容。

允许保留的一类内容，是代码本身为兼容而保留的分支，例如「当 `xlator` 未导出
`xlator_api` 时走旧路径」。这描述的是当前代码事实，不是文档历史。

### 1.2 单一事实来源

同一个事实只在一个文档中完整论述，其他文档用一到两句话概述并链接过去。

- 术语定义只在 [术语表](../overview/glossary.md)；
- 架构分层只在 [架构总览](../overview/architecture.md)；
- 模块内部细节只在对应模块文档，特性文档引用而不复制，反之亦然。

判断方法：如果同一个结论需要在两处同时维护，说明结构有问题，改成「一处定义、多处
链接」。

### 1.3 上下文一致

- 全库针对同一基线，基线只在 [README](../README.md) 声明一次；
- 术语、命名、缩写全局统一，写作前先查术语表，新术语先补进术语表再使用；
- 同一机制在不同文档中的描述不得互相冲突。发现冲突时先修正全局描述，再改局部；
- 文档之间用相对路径互相引用，保证知识库整体移动或克隆后链接仍然有效；
- 代码引用统一使用仓库相对路径与正斜杠，例如 `libglusterfs/src/xlator.c:624`。

### 1.4 结论可溯源到代码

关键结论必须能定位到具体代码位置，格式为 `路径:行号`（`符号名`），例如：

```text
libglusterfs/src/glusterfs/xlator.h:750（struct _xlator）
```

规则要点：

- 行号与符号名必须成对出现。行号随代码变化会失效，符号名保证仍可重新定位；
- 引用定义处或关键分支所在的真实行号，写作时逐个核对，不凭记忆填写；
- 只引用仓库内真实存在的文件，不引用上游网站、外部文档或未提交的代码；
- 单段代码摘录不超过约 10 行，且只在必须展示结构时使用，其余情况用文字描述并给出
  引用位置。

### 1.5 结构清晰

- 每篇文档首行是唯一的 H1 标题，正文从 H2 开始，层级最深到 H4，不跳级；
- 文档开头用一段结论摘要说明「是什么、解决什么问题、关键结论」；
- 超过约 150 行的文档在结论摘要之后、正文之前加「目录」小节，逐条列出各 H2 小节；
  「目录」小节与结尾的「相关文档」小节本身不列入；
- 结尾用「相关文档」小节列出上下游文档，没有则省略；
- 一节只讲一件事，小节标题写成可被检索的名词短语，不写「其他」「杂项」。

### 1.6 准确优先于完备

不确定的内容不写。确需保留但尚未验证的结论，用独立的引用块标注，并在验证后删除该
标注：

```markdown
> 未验证：<具体结论>，验证方式：<如何验证>
```

该标注只表示结论的验证状态，不构成待办事项，也不出现在标题中。

## 2. 目录与命名

```
lmc/
├── README.md            知识库入口：定位、基线、导航、覆盖范围
├── meta/                规范与模板
│   ├── update-rules.md
│   └── templates/
├── overview/            跨模块的整体性描述
├── core/                贯穿全库的核心机制
├── modules/             按模块组织的文档
└── features/            按特性组织的文档
```

约定：

- 目录名、文件名使用英文小写，单词之间用连字符，例如 `call-stack-and-fop.md`；
- 不使用数字前缀，阅读顺序由 [README](../README.md) 的导航表与各目录索引定义；
- 模块文档命名为 `modules/<xlator 或子系统名>.md`，特性文档命名为
  `features/<特性名>.md`，名称与该模块在代码中的标识保持一致；
- 新增、删除、重命名文档时，同步更新 [README](../README.md) 导航表、
  对应目录索引和所有指向它的链接。

## 3. 文档结构

模块文档与特性文档使用 [templates](templates/) 下的模板起步。其余文档按下述骨架组织：

1. 结论摘要（一到两段，无标题或用 H2「概览」）；
2. 主体：概念 → 机制 → 代码位置，由外向内展开；
3. 「相关文档」小节（可选）。

主体中推荐使用小节「代码位置」集中列出本节涉及的引用，避免行内引用过于密集。

## 4. 代码引用规范

| 场景 | 写法 |
| --- | --- |
| 引用文件 | `` `xlators/mount/fuse/src/fuse-bridge.c` `` |
| 引用具体位置 | `` `xlators/mount/fuse/src/fuse-bridge.c:3128`（`fuse_write`） `` |
| 引用目录 | `` `xlators/cluster/` `` |
| 引用配置项或命令 | `` `performance/write-behind` ``、`` `gluster volume set` `` |

行内提及符号时保留英文原名，不改写、不翻译、不缩写，例如始终写 `call_frame_t`，不写
「调用帧结构体」作为指代。

## 5. 交叉引用规范

- 文档间引用使用相对路径链接，例如
  `[架构总览](../overview/architecture.md)`；
- 引用具体小节时附锚点，例如
  `[架构总览](../overview/architecture.md#一次写请求的完整路径)`；
- 链接文字使用目标文档的标题，不写「点击这里」「详情」；
- 引用其他文档的结论时给出摘要加链接，不整段复制；
- 新增文档后检查反向引用：搜索是否有其他文档已陈述同一事实，若有则改为链接。

## 6. 图表规范

- 结构、层次、调用顺序用 Mermaid 表达，一个图只表达一个概念，节点不超过约 15 个；
- 图后必须有一句话说明该图要传达的结论，图不能替代文字结论；
- 图片资源统一放在 `lmc/assets/`，文件名与文档名对应。

## 7. 更新流程

1. 明确主题，确认它属于 `overview/`、`core/`、`modules/` 还是 `features/`，避免与已有
   文档重叠；
2. 阅读相关代码，核对每一个准备写入的结论与行号；
3. 检索已有文档，确认没有重复陈述同一事实，必要时先调整既有文档的职责边界；
4. 按模板或骨架撰写，只写终态内容；
5. 更新 README 导航表与目录索引；
6. 逐项执行第 8 节的检查清单。

## 8. 提交前检查清单

- [ ] 全文没有修订记录、旧结论、`TODO`、草稿或过程性描述；
- [ ] 结论与基线代码一致，所有 `路径:行号` 已逐个核对；
- [ ] 关键结论均有代码引用，且行号与符号名成对出现；
- [ ] 术语与 [术语表](../overview/glossary.md) 一致，新术语已登记；
- [ ] 没有与其他文档重复论述同一事实，重复处已改为链接；
- [ ] 相对链接可达，README 与目录索引已同步；
- [ ] 标题层级连续，长文档有目录，无「其他」「杂项」类小节；
- [ ] 文档只讲一个主题，职责边界与其他文档不重叠。
